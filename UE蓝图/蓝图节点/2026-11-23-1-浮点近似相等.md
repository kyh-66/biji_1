# 浮点近似相等（Nearly Equal (Float)）

判断两个浮点数在容差范围内是否算"相等"，专治浮点比较抽风。

## 干什么用的

浮点数算出来的结果几乎不会精确相等。1.0 - 0.9 不等于 0.1，向量长度算出来是 99.99999 而不是 100。
用 `==` 去比，程序看着对，实际永远走不到那个分支。

这个节点把「差多少以内算相等」这件事显式写出来，判断逻辑就稳了。

## 输入 / 输出

| 引脚 | 类型 | 说明 |
|---|---|---|
| A | Float | 第一个要比较的值 |
| B | Float | 第二个要比较的值 |
| Error Tolerance | Float | 允许的误差，默认 `KINDA_SMALL_NUMBER`（1e-4） |
| Return Value | Boolean | 差值在容差内返回 true |

## 典型场景

- 判断角色是否"到达"目标点：拿 `Vector Length` 算剩余距离，再和 0 比，实际应该和一个小阈值比
- 判断速度是否归零、计时器是否到点
- 判断缩放/血量百分比是否已经等于目标值，比如血条补间结束
- 开关类逻辑里，UI 动画跑完后比对当前值是否等于目标值

## 坑

- **它是绝对值容差，不是相对值。** 比较 1000000 和 1000000.5 时，1e-4 的容差根本不成立，会判不等；
  反之比较两个接近 0 的极小值，1e-4 又太宽松，可能把本该区分的值判成相等。
  数值量级大就用相对误差（自己算 `|A-B| / max(|A|,|B|)`），别硬套这个节点。
- **容差别乱调大。** 有人嫌判断不灵就把 Error Tolerance 改成 1 甚至 10，结果把"没到"判成"到了"，
  角色提前停、技能提前结算，问题更难查。容差应该和你的玩法精度挂钩，不是越大越省事。
- **只比单个 float。** 想比 Vector 请用 `Nearly Equal (Vector)`，或者拆成三个分量分别比；
  直接拿 X 分量代表整个位置是最常见的错。
- 判断方向性的量（比如朝向点积）时，记得先归一化，否则长度会污染比较结果。
