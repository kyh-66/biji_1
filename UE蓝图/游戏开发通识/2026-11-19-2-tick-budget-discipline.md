# Tick 是借来的时间：默认关掉，按需打开

性能问题里最常见的一类，是"什么都没干，帧率就是上不去"。原因往往不是某个算法慢，
而是有几百个 Actor 每帧都在跑一个几乎什么都不做的 Tick。

## 默认姿势：能不开就不开

一个 Actor 只要类里 Tick 是开的，引擎每帧都会为它走一遍调度、调一次回调，
哪怕蓝图里那条 Tick 线后面什么都没接。这种开销单看很小，乘上数量就是 Game 线程的大头。

落地习惯：

- 新建的蓝图类，只要没有逐帧逻辑，进 Class Defaults 把 **Start with Tick Enabled** 关掉
- 需要时再在 BeginPlay 里 `Set Actor Tick Enabled(true)`，用完关回去
- 已经开着的，在蓝图里删光 Tick 节点后引擎会自动提示关掉，别点"否"

## 需要逐帧，也别按满帧跑

- **Tick Interval**：不需要每帧更新的（血条朝向、距离检测、AI 感知）改成 0.1~0.5 秒一次，
  开销直接按比例降
- **Tick Group**：默认在 PrePhysics。跟随相机、挂在骨骼上的东西放到 PostUpdateWork
  可以减少一帧延迟；依赖别人位置的逻辑要设 Tick 依赖，否则会追着上一帧的位置跑
- **Tick Prerequisite**：A 要读 B 的位置，就给 A 加 B 作为前置，别靠"碰巧顺序对"

## 该换掉的几种 Tick

| 在 Tick 里干的事 | 换成 |
|---|---|
| 倒计时、CD | Timer（Set Timer by Event / by Function Name） |
| 一段时间内插值 | Timeline，用完自动停 |
| 等待某个条件成立 | 事件回调、委托、状态机 |
| 每帧查距离决定显隐 | 引擎自带的距离剔除、或降频轮询 |

## 怎么确认自己有没有这个问题

先跑 `stat unit` 看瓶颈在 Game 还是 Draw。Game 高就先怀疑 Tick 数量和蓝图开销，
再用 Unreal Insights 抓一段，按耗时排序看谁在吃时间。**不要凭感觉优化**，
先定位再动手，否则很容易把好代码改成坏代码。

## 一句话

Tick 不是"免费的每帧回调"，是向 Game 线程借的时间。借得越多，帧预算越薄，
留给你真正想做的事的余量就越少。
