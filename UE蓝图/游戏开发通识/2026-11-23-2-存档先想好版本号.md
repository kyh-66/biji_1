# 存档先想好版本号：老存档要能打开

上线之后最贵的一类 bug，不是崩，是**玩家打不开自己的存档**。而这类问题几乎都是第一天就能防住的。

## 为什么第一天就要想

开发期改结构是常态：给 SaveGame 加个字段、换个枚举、把「金币」拆成「金币 + 绑定金币」。
改的时候你本地存档是新的，测试一切正常——因为没人拿两个月前的老存档去开。

等真玩家更新了版本，老存档里没有新字段，读回来是默认值 0：
等级归零、任务进度丢失、背包空了。这类事故修复成本极高，因为数据已经没了。

## 怎么做

1. **SaveGame 里第一个字段就放 `SaveVersion`（int32），从 1 开始。**
   每次结构有不兼容的改动就加一，哪怕只是删了一个字段。
2. **读档时先比版本，再决定怎么补。** 封装一个迁移函数：

   ```
   读档 → 若 SaveVersion < 当前版本 → 按顺序跑迁移步骤（1→2，2→3…）→ 写回新版本号
   ```

   每步只负责一件事，别写一个巨大的 if 分支。
3. **只增不改是最安全的演进方式。** 加字段的风险很低（老档读出来是默认值，通常可接受）；
   删字段、改字段含义、改枚举值顺序，才是真正会崩的组合。
4. **别往存档里塞运行时 UObject 引用。** 存的是「ID / 类路径 + 数据」，读档后再按 ID 重建对象。
   存指针的结果是换个版本就全是空引用。

## 常见的坑

- **枚举删了一项**：老存档里存的是数字 3，新版本里 3 变成了别的东西。要么保留废弃项，要么迁移时做映射。
- **改了默认值却没写迁移**：新玩家和老玩家行为不一致，而且只有老玩家能复现，极难查。
- **存档格式和游戏逻辑耦合**：存档直接存了 UI 状态、摄像机位置，改一次界面就要改一次迁移。
  存档只该存"重新开始游戏时需要恢复的最小集合"。
- **测试只用新档**：留一条固定路径的"祖传老存档"放进自动化测试，每次发版前跑一遍。
  这条比什么规范都管用。

## 一句话

存档格式是**对外契约**，不是内部实现细节。加版本号这一步几乎零成本，
省下的是上线后无法挽回的数据损失。
