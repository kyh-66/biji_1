# 日志不是打得越多越好：先分类，再开口

调试期最容易被忽视的一件事：**日志本身也是要维护的代码**。打得多不是勤奋，是噪音。
真正有用的日志，是三个月后别人（或者明天的你）打开打包版本，能一眼看出"哪一步没走到"。

## 先分等级，别只有"打"和"不打"

UE 的日志分 Verbose / Log / Warning / Error / Fatal 几档，平时只留 Warning 以上，
排查某个系统时再临时把那一类调到 Verbose。用 `UE_LOG` 时带上自己的分类，别全塞 `LogTemp`：

```cpp
DECLARE_LOG_CATEGORY_EXTERN(LogMyAI, Log, All);
UE_LOG(LogMyAI, Warning, TEXT("MoveTo failed: pawn=%s target=%s"), *GetNameSafe(Pawn), *TargetName);
```

分类的好处很实在：`LogTemp` 是垃圾桶，几十个系统混在一起，出问题时你得一屏一屏地翻。
有自己的分类，一行控制台命令就能单独把这一块打开或静音。

## 每条日志都要能回答"谁、哪一步、什么值"

三种最常见的废日志：

- `UE_LOG(LogTemp, Log, TEXT("here"));` —— 不知道是谁的 here
- `UE_LOG(LogTemp, Log, TEXT("AI moving"));` —— 哪个 AI，往哪走
- Tick 里无条件打印状态 —— 一秒刷 60 行，旁边的关键行被冲走

改成带上关键上下文（对象名、状态机当前状态、目标坐标或血量这种数值），
再配一个"只在状态变化时打"的门槛，日志量能降两个数量级，信息量反而变高。

## 蓝图里的 Print String 要当临时工具

蓝图 `Print String` 方便，但它有几个代价：**打包后依然会打**（除非自己套编译开关），
同一帧多条会互相覆盖看不出顺序，而且每条都要转字符串、拼字符串，在 Tick 里很贵。
排查完就删，或者收进一个 `bDebug` 布尔后面。真想留下来长期用的，做一个小函数封装，
统一加前缀和序号，比如 `[AI-03]`，一帧打三条也能看出先后。

## 打包之后才是真考验

Editor 里再清楚的日志，Shipping 包里默认只保留 Warning 及以上。
所以**关键路径上的失败一定要用 Warning 或 Error 打**，不要全是 Log：
玩家反馈"卡住了"的时候，你能拿到的往往只有客户端日志，那一行 Warning 就是全部线索。

反过来，频繁触发的正常流程（比如每次开火、每次生成子弹）千万别用 Warning，
否则日志文件几分钟就上 G，玩家的硬盘和你的排查时间一起被吃掉。

## 一句话

日志的目标不是"证明我写了代码"，而是"出问题时，能在十行之内定位到哪一步断了"。
按这个标准去砍，大部分打印都该删。
