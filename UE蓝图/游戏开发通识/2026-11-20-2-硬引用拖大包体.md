# 硬引用比你想的宽：包体是"被拖进来的"，不是"被用到的"

很多人以为"这个资源我只是在某个分支里用了一次，打包时应该不会带进去吧"——错。
硬引用是**编译期就成立**的关系，跟运行时走不走那个分支毫无关系。

## 现象

- 一个只有 Boss 关卡才用的 200MB 场景，出现在新手村地图的引用链里
- 主菜单 Blueprint 里为了取一个枚举，引了整张 DataTable，连带几百个图标全打进首包
- 打包后发现资源目录 12G，逐条查 Reference Viewer，才发现是某个"全局常量"类拖的

## 为什么会这样

硬引用（Hard Reference）在蓝图里表现为：**你把一个资源直接拖进变量类型、或者在节点上选了一个具体资源**。
这时候序列化会把它的完整路径写进蓝图，加载器会连带把它依赖的一切都加载进来。
**判断标准不是"我有没有执行到那个节点"，而是"它的路径有没有被写进这个资产"。**

## 怎么处理

1. **先量，再改**。打开 **Reference Viewer**（右键资源 → Reference Viewer），看谁指着它。
   再来一次 **Size Map**，看谁最占地方。不打这两枪就动手，全是在猜。
2. **分类硬引用**：
   - 常量、枚举、配置：这些本来就该常驻，硬引用没问题
   - 大块美术、音频、关卡：**一律走软引用**
3. **软引用的落点**：
   - 蓝图变量类型选 **Soft Object Reference / Soft Class Reference**，存路径不存实例
   - 用 **异步加载资产（Async Load Asset）** 或 **异步加载类（Async Load Class）** 拉进来，加载完在回调里 Cast 再用
   - 小资源、必用的贴图可以用 **软引用 + 预加载**，别每次现场加载
4. **首包瘦身的工具**：
   - **Primary Asset Label**：给一组资源打标签，声明"这是可选包"，配合 Chunk 分配
   - **Asset Manager** 的 Primary/Secondary Asset 划分，把可下载内容和核心内容隔开
   - 项目设置里开 **Share Material Shader Code** 之类的合并选项，别让同一个材质在多个包重复编译

## 经验

- **软引用不是万能药**：用了软引用就得处理"没加载好"的情况——空指针、白模、静音。这套异步流程比硬引用麻烦得多，别为了"看起来规范"到处乱套。
- **只在真正的大块、并且确实不是随时都要用的资源上用**。用得太碎，代码里全是 Async Load 回调，维护成本比省下的包体贵。
- **包体问题 90% 出在几个"没想到"的地方**：主菜单、全局配置蓝图、GameMode 的默认值、一个不小心勾了"在启动时加载"的资产。
- **每次打包前跑一次 Size Map 和资源审计**，把这个动作放进检查流程。等到发版前一周才发现多出 8G，改都改不完。
