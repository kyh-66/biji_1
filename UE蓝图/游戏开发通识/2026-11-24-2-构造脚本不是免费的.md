# 构造脚本不是免费的：关卡加载慢，先查 Construction Script

## 一句话

`Construction Script` 不是「编辑器里预览用的」，它在**运行时也会执行**——对象被生成或关卡被加载时各跑一遍。
里面写的逻辑越重，加载和 Spawn 就越慢，而且这类卡顿在 Profiler 里常常找不到，因为它发生在游戏开始之前。

## 为什么会踩

蓝图里改个材质颜色很方便，于是有人在 Construction Script 里：
遍历场景里所有 Actor、做一次射线检测、读表、生成子组件、计算导航……

编辑器里点一下就看得到结果，感觉「这是编辑器的事」。实际上：

- **运行时 Spawn 该类对象 → 跑一次 Construction Script**
- **关卡加载时，场景里所有实例 → 各跑一次**
- **PIE 和打包后都会跑**

一个关卡放 200 个这样的道具，加载时就是 200 次构造，每个里面再射线检测 10 次，就是 2000 次同步查询卡在开场黑屏里。

## 怎么判断

1. 打开关卡明显慢，但 `stat unit` 在游戏里一切正常 → 先怀疑加载期。
2. 在 Construction Script 开头加日志，打包后看启动日志里刷了多少行。
3. 用 Unreal Insights 打开 **Loading** 轨道，看 `Construction` 段的耗时——比自己猜准得多。
4. 对比法最省事：把关卡里某类道具全删掉再开，慢不慢一目了然。

## 怎么改

- **能预计算的，移到资产里做**：材质参数、静态网格的组合、初始变换——在编辑器里摆好存下来，别运行时算。
- **能烘进数据的，用 DataAsset / DataTable**：构造脚本读表算值，不如直接读算好的值。
- **必须运行时算的，挪到 `BeginPlay` 或延迟初始化**，把成本从「开场统一卡」摊到实际用到的那一刻。
- **批量逻辑不要写在每个对象的构造里**，写成一个 Manager 在关卡开始时统一处理一遍。
- **编辑器专用逻辑包在 `Is Editor` 判断里**（蓝图节点 `Is Editor` / 用 Editor Utility），保证打包后这段不占时间。
- 子组件的创建尽量在构造时就固定下来，别在运行时动态加删组件。

## 顺带一句

同类的还有 `Event Tick` 和 `BeginPlay` 里的一次性重活、以及 `Spawn Actor` 时传的重初始化参数。
**凡是「每个实例都跑一遍」的东西，数量一上去就是指数级代价**——先问一句「这东西真的需要每个实例都算吗」。
